## Attention cache storage (September 21, 2026)

Attention publication validates the complete row array and stores a lossless gzip/base64 encoding when it fits the 12 MB inline budget. The reader accepts both this encoding and the previous inline/chunk representation. Cursor identity, ordering, filters and counts are unchanged. The September 22 availability successor below changes expiry. The decoded payload is capped at 64 MB; larger publications retain the existing chunk path. A measured production snapshot of 6,394 rows decreased from 26,761,829 JSON bytes to 1,242,624 encoded bytes. This matters on the shared 512 MB Atlas cluster: multiple full snapshots had caused storage-quota write failures. Superseded cache documents are disposable after their dated `expires_at`; the latest successful snapshot has no expiry. Customer evidence and audit retention are unchanged. Rollback to a reader without compression or null-expiry support requires publishing a compatible dated snapshot first.

## CSI-15 historical activation

Historical capture persists attachment work but defers Outreach and recording discovery until safe activation. `backfill/readiness.ts` prevents `ensureInteraction` (including generic repair and attachment hooks) from activating a historical call while later planned capture or its number's paged attachment work is incomplete. Existing fulfillment and official Booked/Cancelled checks remain the only lifecycle authority; no parallel historical Outreach engine exists.

Missed-call and Intelligence follow-up creation audits retain the source time, and Outreach/Number Review opening uses its original trigger time. Capture time remains observable separately. ## Lead progress, CRM disposition and time sorts (LP-01/03/06, September 22, 2026)

- **One consumer.** Accepted canonical Lead writes emit an `EntityChange`; the minute scan raises `outreach-lead:` jobs whose `input_refs[1]` is the change id; `ensureLead` is the Lead projection (§13.3 H1). `outreach/leadProgress.ts` is the pure policy: `0` fresh, `1` quoted, `3` rep discretion, `7` CRM bad/unusable, `8` CRM dead opportunity; other valid codes unmapped; missing Unknown. Stored `quoted` is read as its own evidence and never recomputed from the code.
- **Projection.** `OutreachRecord.lead_progress` stores current Priority/Quoted, disposition, `work_observed`, basis (`quoted`, `priority_assigned`, `priority_changed`, `historical_snapshot`), provenance (`accepted` when, judged per field over the last 25 changes touching those paths, a change vouches for the current value; else `uncertain`), the accepted change/observation/decision ids, `source_applied_at` (known accepted time), `first_work_observed_at`, `last_progress_at` (only a semantic change sets it), a semantic `fingerprint` and a `disposition_revision`. An identical re-delivery writes nothing: no save, no audit, no job. `projected_at` is processing time and is never a business time.
- **Transitions (§4 order).** Authoritative closure (`transitions.ts` `authoritativeClosure`: the Lead's official flags or an exact `booked_leads` row, §11.1) → Owner closure/override → identity review → CRM disposition → Lead progress → action-state derivation. Accepted `1`/`3` or `quoted=true` on an eligible Unworked record sets `open`; Band 2 clears because it requires Unworked; Band 5 follows when no action exists, with the secondary reason `no_call_observed`. Nothing sets call timestamps, counters, responsibility, promises or messages. H1a: the "no calls remain" reversion requires `!lead_progress.work_observed`; leaving identity review restores Open when progress exists (`restoreFromIdentityReview`).
- **CRM disposition.** Accepted `7`/`8` closes through `closeRecord(record, "granot_bad_unusable" | "granot_dead_opportunity", "crm_disposition")`: outstanding actions are cancelled with that basis (never completed); official flags, CPL, billing and sheet routing are untouched; no `number_refresh` (paid analysis) nomination is raised for this closure. `7 ↔ 8` refreshes the reason and keeps the closure history. A later nonterminal code queues one deduplicated `disposition_reopen` review and the record stays closed until an explicit Owner `reopen` (which revives no action). A terminal value with uncertain provenance does not close: it opens a `disposition_review`, derive adds the `disposition_review` call blocker, and `create_followup` / `set_waiting` / `start_call` answer `DISPOSITION_REVIEW`. Official and Owner closures keep their stronger reason.
- **Owner commands.** `reopen` on a `crm_disposition` closure is allowed only when the disposition moved on (`CRM_DISPOSITION_CLOSED` otherwise). `override_disposition { disposition_revision, reason }` is revision-scoped: it reopens under the current terminal code, writes an Owner instruction and audit, survives identical redelivery and expires on a semantic disposition change; it never bypasses official closure or a suppressed Number. `mark_worked`, `create_followup`, `set_waiting`, `start_call` answer `CRM_DISPOSITION_CLOSED` while an un-overridden terminal disposition is current.

## Card facts and reference time (S1-FACTS, September 23, 2026)

- **`facts`.** `outreach/facts.ts` `outreachFacts({ record, followups, number, lead, bookings, cancellations, now })` is pure and has two callers through `toOutreachDto`: the Attention publish (frozen on each snapshot row at publish time) and `GET /outreach/:id` (at request time). It returns `{ facts, sort_keys, filter_keys, outcome }` (S2-DESK below). `outreachDtoSchema.facts` is optional so snapshots published before it still parse.
  - `route`: `moveViewsForLead(lead, model).canonical_current`, the same view as Move details; `move_date` is YYYY-MM-DD and Form Leads only; `null` without a Lead (Number-only subjects).
  - `last_call_at`: max of the primary Number's `rollups.last_inbound_at` / `last_outbound_at`. `calls_total`, `conversations_total`, `recordings_available`, `recordings_analyzed` read `interactions_total`, `human_conversations_total`, `recordings_total`, `conversations_analyzed_total`. With no primary Number every one of these is `null` ("No Number on file"), never 0.
  - `newer_call_since_assessment`: `last_call_at > move_assessment.latest_conversation_at`, only when assessment applicability is `active` (the gate `moveAssessmentProjectionDto` uses).
  - `details_disagree`: `move_assessment.conflict_targets` contains `pickup_location`, `delivery_location` or `move_date`; a purged projection never disagrees. The assessment publish writes `conflict_targets` (`artifact.conflicts[].affects`, deduped) with the projection (`projectionFor`); projections published before this read `[]` until their next publication.
  - `next_action_state`: from `record.next_action` (open follow-ups only) with `derive()`'s `attentionDue` and `<= now` boundary, so `overdue` is exactly `derived.overdue` for the action. Closed and identity-review work reports `none`, as `derive()` treats it as not actionable. A snooze postpones the reminder, so a passed contractual `due_at` under a snooze is `due`.
  - `move_date_passed`: `route.move_date < today`, today in America/New_York (flips at ET midnight, not UTC). The same boolean is passed to `moveAssessmentProjectionDto(record, pending, { moveDatePassed })`, which derives the assessment's `stale_reason: "move_date_passed"` on read.
  - `rep_thread`: `null` until rep threads ship.
- **Reference time (data spec §3.8).** Every state above is decided at the caller's `now`: the snapshot's `as_of` for `GET /attention`, request time for `GET /outreach/:id`. The function never reads the process clock; the Admin only formats durations between a server time and `as_of`.
- **Sort keys and the rep filter.** `attentionSortKeys` adds `last_call` and `interactions` from the row's frozen `facts` (null without facts or without a Number); both are selectable sorts since S2-DESK. `agent_id` also matches follow-ups whose `promised_by` is the rep (D7), besides the record and follow-up assignees.
