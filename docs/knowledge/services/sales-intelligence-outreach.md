# Outreach and follow-ups — CSI-06

September 22 availability repair: five minutes is now a **freshness** threshold, not the lifetime of the latest successful Attention list. Publication stores the new header and any chunks with `expires_at: null`; in the same transaction it assigns older retained snapshots a five-minute TTL for existing cursors. Only cache deletion metadata changes; row contents and snapshot/cursor identities remain immutable. An incomplete or failed build leaves the previous successful list available. `readAttention` returns `status: ready` plus optional `stale: true` after the freshness threshold, with the original `as_of`. Admin displays the delayed-refresh notice and keeps the rows visible. Commands still validate current server state. Before the first successful publication, `pending_projection` remains honest. No index migration or environment change is needed: the existing TTL index ignores null dates. Legacy dated snapshots remain readable until their existing expiry. Rolling back readers removes visibility of retained null-expiry snapshots until the old publisher successfully creates a dated one.

September 21 targeted Outreach backfill: `scripts/backfill-outreach-intelligence.ts` inventories the last 45 days of Form Leads and Call Leads against captured Contact Numbers, excludes official closure and matching Booking records, and selects a bounded mix of both channels. Apply rechecks eligibility, uses the existing attachment/Outreach services, replays attributable calls newest first, and processes at most two distinct recorded interactions per selected opportunity through the existing media/transcription/analysis/application workers. Normal budgets, retries, identity gates and Owner precedence remain authoritative. Reports contain IDs and operational outcomes, not transcripts or customer phone numbers. `--resume` reuses a less-than-24-hour inventory; `--apply` enables writes. No contact messages or official Lead/Booking mutations are performed.

Going cold distinguishes a future agreed deadline from a reminder snooze. Snoozing an already-overdue action postpones that action's Attention deadline but does not suppress Going cold. A genuinely future due/base Attention date still does, including a day-only wait's next staffed opening. Human contact remains the only reset of the cold-contact age.

A review whose Conversation no longer supplies a Number stays stored but cannot create a navigable Attention row. The full snapshot remains atomic; the latest successful snapshot stays readable and superseded snapshots retire five minutes after replacement; no partial list is published when the 90-second budget is exceeded. `staffing.ts` implements Eastern Mon–Sat 08:00–20:00 defaults through persisted policy: 30 staffed minutes first call, 15 missed callback, 1440 Going cold. Notes preserve context without implying contact. Overall/action ownership are separate; Owner assignments persist. Snooze changes Attention time while preserving contractual due time; undated snooze is invalid. Close cancels, reopen does not revive obligations, and live official eligibility/permanent suppression still block reopen.

`effects.ts` owns pure planning plus transactional application. Team D supplies validated run-scoped findings and server-resolved intents, never arbitrary updates. Recheck current revisions, event identity, official closure, Owner field instructions and later calls. Source interaction identity and original source date remain separate from completion evidence and the current deadline; repeated extraction resolves the original commitment even after completion or Owner date correction. Multiple possible callback targets require completion review; an actual call cannot silently complete every independent callback. The append-only effect ledger retains outcomes across runs and returns the actual effect target. `review/restrictions.ts` serializes number-level spoken restrictions and preserves Owner resolution across replay. Restrictions block execution without rewriting Owner plans or closing Outreach.

`derive.ts` computes all reasons, the highest-priority band, per-action/record responsibility, human-contact ages, cooldown and blockers using every open action. `reads.ts` exports Owner DTOs with all actions and plural Number detail Outreach rows. Reads do not mutate. Outreach DTO optionally carries `lead_attachment` and `call_progress`; DerivedDto optionally carries `call_state` and `provenance_state`, both derived on read. `certainty_label` comes from `certaintyLabel()`. `/outreach/:id`, `/outreach/by-lead/...`, `/numbers/:id` and `/attention` share those fields. `allowed_actions` includes `start_call` / `end_call` with the same blockers the commands enforce. Blocker codes stay inside `CSI_ERROR_CODES`; both a closed record and a call already in progress return `ILLEGAL_TRANSITION`, and `derived.call_state` is what distinguishes them. `attention.ts` builds immutable snapshots in the worker; GET cursors bind snapshot/filter/as-of and do not create snapshots. An unavailable projection is `pending_projection` with a nullable count, not a false zero. Snapshot build aborts without partial publication at its 90-second budget. Storage uses compression or chunks as described below.

`reactToAttachmentChanged` recomputes a bounded `lead_attachment` + `lead_attachment_revision` display mirror of the deciding `NumberLeadAttachment` edge inside the same attachment-change transaction, via `refreshRecord(..., "outreach_lead_attachment_mirrored", …)`. The mirror follows the record's primary Contact Number only. Closed records are skipped (pre-existing loop). Ambiguous or competing identity is stored as Ambiguous and never picks a Lead. The revision is monotonic on the Contact Number revision: an older change cannot clobber a newer mirror. `decided_by` is `owner` when the edge has Owner `decided_at`, `automatic` when `auto_decision` is present, otherwise `evidence`. Confidence is populated only for an automatic decision.

`call_progress` is Owner Call state on the Outreach Record. It is a separate field; `CSI_OUTREACH_STATES` is untouched and Call state is not a new official Outreach state. `start_call` / `end_call` run through the existing `POST /outreach/:id/commands` path (`recordForUpdate`, Idempotency-Key, `ownerInstruction`, audit). `start_call` writes `call_progress` only: it never changes Outreach state, contacts nobody and completes no action. It is blocked when the record is closed (`ILLEGAL_TRANSITION`), when a call is already in progress (`ILLEGAL_TRANSITION`), and by the same active call restriction that gates dialling (`CONTACT_RESTRICTED`). Starting again after an ended call replaces the field; the audit rows are the history. `ensureInteraction` ends a running call when an attributable Call Interaction covers the started window, using only that interaction's own span (widened backwards by the same duration for the dialling gap) and stamping `interaction_id`.

`worker.ts` registers `outreach_ensure` on the existing job dispatcher, minute cron and stage recovery. Queue payload is only `{job_id}`; current interaction comes from `input_refs`. EntityChange scanning uses `(applied_at,_id)`. All writes remain inside the CSI TEST_MODE database boundary. Flags default off. No routine call/note sends messages, invokes a model, or modifies Lead/Booking/Agent records.

Bounded maintenance (September 21, 2026; [17 §6](../../call-sales-intelligence-new/17-storage-throughput-and-llm-efficiency-handoff.md), [18](../../call-sales-intelligence-new/18-efficiency-implementation-2026-09-21.md)). `runOutreachEnsureOnce` keeps three causes of work separate and every durable job key semantic:

- **Source change.** EntityChange rows for Form/Call Leads raise `outreach-lead:` jobs keyed by the change id, as before.
- **Time boundary.** An indexed query over open `wait` follow-ups whose `due_at` has passed and whose `wait_expired_at` is unset raises one `outreach-clock:` job per boundary (`waitExpiryNomination`: key carries the follow-up id and the exact due instant). A re-dated or snoozed wait is a new boundary. This is the only clock the worker persists: first-action deadlines, follow-up due times, snooze and restriction expiry and Going cold are derived on read by `derive()` and republished by the Attention cron, so no job exists for them.
- **Repair sweep.** Rolling `_id` pages over Form Leads, Call Leads, canonical Call Interactions and **non-closed** Outreach Records (`outreachRepairNomination`). Leads are keyed by their official flags, calls by `projection_revision`, Outreach Records by their own `revision`. The former Outreach Record key carried the sweep-cycle timestamp, so every cycle inserted one completed no-op job per record; that family was about 61,900 of the 90,000 stored jobs. A frozen corpus now hits the dedupe fence on every later sweep and inserts nothing. Closed records are not swept: official closure cannot move them and only an Owner command reopens them.

Attachment fan-out is coalesced: an attachment revision raises one `outreach-number:` job per Contact Number revision (`replayNumberInteractions`), which replays the number's canonical calls in keyset pages of 25 with a continuation job, instead of one `number:` job per call. Per-call `number:` jobs remain the shape of interaction repair and queue wake-ups.

## Attention cache storage (September 21, 2026)

Attention publication validates the complete row array and stores a lossless gzip/base64 encoding when it fits the 12 MB inline budget. The reader accepts both this encoding and the previous inline/chunk representation. Cursor identity, ordering, filters and counts are unchanged. The September 22 availability successor below changes expiry. The decoded payload is capped at 64 MB; larger publications retain the existing chunk path. A measured production snapshot of 6,394 rows decreased from 26,761,829 JSON bytes to 1,242,624 encoded bytes. This matters on the shared 512 MB Atlas cluster: multiple full snapshots had caused storage-quota write failures. Superseded cache documents are disposable after their dated `expires_at`; the latest successful snapshot has no expiry. Customer evidence and audit retention are unchanged. Rollback to a reader without compression or null-expiry support requires publishing a compatible dated snapshot first.

## CSI-15 historical activation

Historical capture persists attachment work but defers Outreach and recording discovery until safe activation. `backfill/readiness.ts` prevents `ensureInteraction` (including generic repair and attachment hooks) from activating a historical call while later planned capture or its number's paged attachment work is incomplete. The activation worker processes only calls in the completed window's half-open `[window_from, window_to)` interval, newest first, ten per fenced continuation, before moving to older source calls. Existing fulfillment and official Booked/Cancelled checks remain the only lifecycle authority; no parallel historical Outreach engine exists.

Missed-call and Intelligence follow-up creation audits retain the source time, and Outreach/Number Review opening uses its original trigger time. Capture time remains observable separately. A successfully completed batch does not spend a transient retry. Retention removes derived follow-up content with a readable tombstone and preserves non-content source/effect identity. Synthetic fulfillment, official-close, chronology and recovery proof: [CSI-15 checks](../../call-sales-intelligence/workspace/evidence/csi-15/CHECKS.md).

## Lead progress, CRM disposition and time sorts (LP-01/03/06, September 22, 2026)

Contract: [Lead progress specification](../../../../sales-intelligence-move-assessment-workspace/SALES-INTELLIGENCE-LEAD-PROGRESS-SPECIFICATION.md) §§3–4, 6, 11, 13–14; agreed interfaces in [LP-01 contract](../../../../sales-intelligence-move-assessment-workspace/evidence/LP-01-CONTRACT.md). Flag `SALES_INTELLIGENCE_LEAD_PROGRESS` (default off). Off keeps `ensureLead` and the repair fingerprint exactly as before.

- **One consumer.** Accepted canonical Lead writes emit an `EntityChange`; the minute scan raises `outreach-lead:` jobs whose `input_refs[1]` is the change id; `ensureLead` is the Lead projection (§13.3 H1). `outreach/leadProgress.ts` is the pure policy: `0` fresh, `1` quoted, `3` rep discretion, `7` CRM bad/unusable, `8` CRM dead opportunity; other valid codes unmapped; missing Unknown. Stored `quoted` is read as its own evidence and never recomputed from the code.
- **Projection.** `OutreachRecord.lead_progress` stores current Priority/Quoted, disposition, `work_observed`, basis (`quoted`, `priority_assigned`, `priority_changed`, `historical_snapshot`), provenance (`accepted` when, judged per field over the last 25 changes touching those paths, a change vouches for the current value; else `uncertain`), the accepted change/observation/decision ids, `source_applied_at` (known accepted time), `first_work_observed_at`, `last_progress_at` (only a semantic change sets it), a semantic `fingerprint` and a `disposition_revision`. An identical re-delivery writes nothing: no save, no audit, no job. `projected_at` is processing time and is never a business time.
- **Transitions (§4 order).** Authoritative closure (`transitions.ts` `authoritativeClosure`: the Lead's official flags or an exact `booked_leads` row, §11.1) → Owner closure/override → identity review → CRM disposition → Lead progress → action-state derivation. Accepted `1`/`3` or `quoted=true` on an eligible Unworked record sets `open`; Band 2 clears because it requires Unworked; Band 5 follows when no action exists, with the secondary reason `no_call_observed`. Nothing sets call timestamps, counters, responsibility, promises or messages. H1a: the "no calls remain" reversion requires `!lead_progress.work_observed`; leaving identity review restores Open when progress exists (`restoreFromIdentityReview`).
- **CRM disposition.** Accepted `7`/`8` closes through `closeRecord(record, "granot_bad_unusable" | "granot_dead_opportunity", "crm_disposition")`: outstanding actions are cancelled with that basis (never completed); official flags, CPL, billing and sheet routing are untouched; no `number_refresh` (paid analysis) nomination is raised for this closure. `7 ↔ 8` refreshes the reason and keeps the closure history. A later nonterminal code queues one deduplicated `disposition_reopen` review and the record stays closed until an explicit Owner `reopen` (which revives no action). A terminal value with uncertain provenance does not close: it opens a `disposition_review`, derive adds the `disposition_review` call blocker, and `create_followup` / `set_waiting` / `start_call` answer `DISPOSITION_REVIEW`. Official and Owner closures keep their stronger reason.
- **Owner commands.** `reopen` on a `crm_disposition` closure is allowed only when the disposition moved on (`CRM_DISPOSITION_CLOSED` otherwise). `override_disposition { disposition_revision, reason }` is revision-scoped: it reopens under the current terminal code, writes an Owner instruction and audit, survives identical redelivery and expires on a semantic disposition change; it never bypasses official closure or a suppressed Number. `mark_worked`, `create_followup`, `set_waiting`, `start_call` answer `CRM_DISPOSITION_CLOSED` while an un-overridden terminal disposition is current.
- **Reads.** `outreachDtoSchema.lead_progress` (optional): raw code, server labels (`priority_label`, `disposition_label`, `basis_label`), provenance, source origin and known time, closure basis, override, reopen review id, `explanation` ("Lead updated in Granot · No next step set" / "Quoted · No next step set" / "Lead updated · No next step set") and `no_call_observed`. `allowed_actions` gains `override_disposition`. `loadAttachedLeadProgressForNumbers` gives the Numbers list the one resolved Lead's progress and Booking, or an explicit `multiple` / `none`; facts are never merged across Leads. The projection is frozen into Attention snapshot rows, so the card and the server band share one `as_of`.
- **Worker (H2/H3).** The entity-change scan re-reads the trailing two minutes on every pass (commit-lag gap) and advances the strict cursor only from the page beyond it; per-change dedupe (`csi:outreach:entity-change:v2:<id>`, versioned because the job now carries the change id) makes re-enqueue a no-op, and a row whose stored payload disagrees is skipped and logged (`outreach.entity_change_job_conflict_skipped`) rather than pinning the cursor. A create or a contact/eligibility path change also raises the `attachment-lead:` job (`leadAttachmentJobInput`), with the 5-minute watermark as backstop. With the flag on, the Lead repair fingerprint includes `granot_priority` and `quoted`, so the sweep recovers a missed accepted change within one lap; off keeps the old key so no mass re-nomination happens before the dry run.
- **Time sorts (§14.1).** `GET /attention` accepts `sort=attention|next_action_due|lead_received|last_human_contact|last_lead_progress`, `direction`, `view=attention`. Publish freezes `sort_keys` per row (`attentionSortKeys`); the read filters, sorts the whole snapshot (nulls last in both directions, ties on `subject_key`), then paginates; the cursor digest binds sort, direction and view for non-default sorts and keeps the previous shape for Attention order. Score sorts and `all_outreach` are added by Move assessment on the same enum. Numbers list sorts live in [Number Activity reads](number-activity-reads.md).
- **Move assessment sorting and all-Outreach view (MA-04).** `GET /attention` adds `sort=transaction_intent|move_likelihood` (default `desc`), `view=attention|all_outreach` and `freshness=fresh|all` (absent = `all`). Publication builds **one** frozen list for both views: band/badge rows as before (`in_attention: true`) plus every other non-purged record whose stored state is not `closed` (`in_attention: false`), built from the same batched inputs/side data; the queued-assessment set is one `distinct` per publish. Each row carries `outreach.move_assessment` (compact projection, applicability applied: closed or accepted un-overridden terminal disposition → `not_applicable` with null scores; `purged`/`failed` → null; `ready` with null → assessed Unknown; queued job → `pending`; nothing → absent = Not assessed) and `sort_keys.transaction_intent/move_likelihood/assessment_status/assessment_stale`. `view=attention` keeps `in_attention !== false` (unmarked older rows stay), so the default population, order and cursor are unchanged. `view=all_outreach` returns every row except `closed` ones unless `state` explicitly includes `closed`; closed records without a band or badge are not in the snapshot at all (their historical scores are read through [Move assessment reads](sales-intelligence-move-assessment.md)). `freshness=fresh` drops `assessment_stale === true`. Score order: filter → global numeric sort → paginate; nulls last both directions, ties on `subject_key`, no band/confidence prefix. Cursor digest: the default request (Attention order, Attention view, no `fresh`) keeps `payloadHash(filters)`; otherwise `payloadHash({ ...filters, sort, direction, view, freshness? })` (`freshness` only when `fresh`, so LP-06 time-sort cursors still resolve); any change is `INVALID_INPUT`. Publish cost grows with the number of open non-band records; measure with `scripts/time-csi-attention-pages.ts` before enabling the Admin score view.
- **Number rollups for the Last human conversation sort.** Capture never labels a call a human conversation; findings (`effects.ts`) and the Owner (`set_contact_type`) do. Each of those writes now queues the Number's durable `rebuild` job in the same transaction when the label crosses the human-conversation boundary (`queueNumberRollupRebuild`), so `rollups.last_human_conversation_at` / `human_conversations_total` follow the label without a second rollup owner. Existing rows need one `enqueueRebuildAll` after deploy.
- **Reconcile.** `scripts/reconcile-lead-progress.ts` (dry run by default) inventories both Lead types and the §13.4 buckets through `completeNormalizedMatchSet`; `--apply --pilot N` / `--apply --resume` runs `ensureLead` in transactional pages of 100 with a checkpoint under `scripts/dev_ops/output/`, policy `lead-progress-v1`, zero model calls, and refuses production without `--allow-production`. Replica proof: `pnpm test:csi:lead-progress:replica` (`scripts/dev_ops/test-csi-lead-progress.replica.test.ts`).
- **Move assessment hooks (MA-02).** The entity-change scan calls `nominateMoveAssessmentForChange` for Lead changes touching move fields (flag `MOVE_ASSESSMENT`), and `closeRecord`/disposition changes need no model call because assessment applicability is derived on read. Details: [Move assessment](sales-intelligence-move-assessment.md).
