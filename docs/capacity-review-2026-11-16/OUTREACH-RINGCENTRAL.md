# Outreach, Numbers and RingCentral capacity review

Status: **planning evidence, no runtime edits, production mutations, index changes or tests executed by this review**. Code inspected November 16, 2026 New York. Live sizes below come from the root agent's read-only `evidence/inventory.json`, captured November 16 at 8:13 p.m. New York (2026-11-17T01:13:38Z); prior capacity-brief figures are not remeasured here.

## Outcome needed

Reduce the operational work generated by each unchanged Granot snapshot without removing Call Qualification, current Desk freshness, historical rep performance or ordering evidence. The highest-value lever found in this scope is **receipt-keyed Outreach refresh fan-out**, not deleting historical Calls or SMS facts. A second material finding changes the proposed immediate cleanup: some completed CSI jobs are the only source of the Desk's 14-day admissions history.

## Findings and code evidence

### OR-1 — a successful Estimates receipt generates new Desk work even when nothing changes

`src/services/granotHttpCollector/estimatesOutreachRefresh.ts:31–55` accepts `applied`, `linked` and `already_current`, reads its Decision, refreshes Pool membership and nominates an `outreach_lead_change` job for an existing open subject. Its dedupe key includes the **lifecycle receipt ID**, not a semantic Lead fingerprint. Distinct unchanged captures therefore intentionally have distinct jobs.

`src/services/salesOutreach/subjects/leadChangeJob.ts:134–136` then explicitly enqueues `outreach_evaluate` for that receipt whenever the subject remains open and admitted, including when `refreshLeadForOutreach` returns `unchanged`. Meanwhile `syncSubject` can enqueue its usual subject-revision evaluator (`subjects/sync.ts:214–244`, `subjects/store.ts:423`). Thus a changed subject may get both a revision-caused evaluator and a receipt-caused evaluator. The second is not necessary when the first is already guaranteed to consume that committed state; that proposition still needs a replica concurrency proof before changing behavior.

The current code preserves periods correctly: repeated priority does not create another policy period. It still copies `priority.accepted_at` and `priority.observation_id` into the subject (`subjectBuilder.ts:89–113`), so a fresh same-value accepted Observation changes subject metadata. Only `lead_revision_seen` and `decision_fingerprint` count as evaluator-free bookkeeping (`sync.ts:293–297`); changed accepted evidence does not. Pool membership similarly compares accepted Observation ID and Lead revision (`pool/admission.ts:229–244`). These bounded document updates cost oplog/I/O even when they do not add business records.

An evaluation is not a cheap early no-op: `evaluation/evaluateJob.ts:74–137` reads periods, plans, restrictions, assignments, contact events, coverage and rep identity, runs the engine, and retains SMS requirements **before** it compares the projection result fingerprint. An unchanged projection still incurs that work, plus job insert/claim/completion writes. `performance/evidence.ts:112–270` reads every retained requirement day for the subject and may inspect frozen policies and corrected evidence; this cost grows with history.

**Proposal, in two releases:**

1. Remove duplicate *evaluation nomination* within one Estimates refresh transaction. Have subject sync return an explicit `evaluation_requested` signal. Keep the explicit repair evaluator only when sync did not already request one. Do not infer this from `outcome: updated` because bookkeeping-only updates deliberately request no evaluation. Preserve the unchanged-subject repair path in this first release.
2. Introduce one durable refresh state per canonical subject/Lead, with requested and consumed generations, semantic inputs and a separate accepted-evidence freshness watermark. Multiple receipts can request work against the same pending state; a worker that races a newer request must leave it pending. Retain the Granot temporal acceptance and receipt/Observation/Decision contract unchanged. Only suppress downstream evaluation when every evaluator-relevant input is unchanged and there is no due clock/coverage repair. A generation or revision is required in the claim fence so completion cannot erase a newer wake-up.

The semantic input contract must include current Lead facts, priority uncertainty, contact-number linkage, relevant assignment/identity revisions, configuration decision/policy fingerprints, Pool state, and the clock/coverage repair cause. An unchanged raw row hash alone is insufficient. Fresh accepted evidence may resolve uncertainty or enable Pool admission even when visible values match. Closed subjects must remain closed. An unchanged refresh still needs a bounded recovery route for an earlier lost downstream callback.

This design reduces downstream job rows without first changing immutable Granot evidence semantics. It is separate from the larger evidence-compaction amendment. Expected row savings must be calculated from live job cause/outcome counts, not assumed to equal every Granot receipt.

### OR-2 — the proposed blanket three-day CSI cleanup loses supported history

`src/models/salesIntelligence/infrastructure.ts:28–49` declares a 14-day `completed_at` TTL. `enqueueCsiJob` is already insert-only with timestamps disabled (`salesIntelligence/jobs.ts:25–75`): re-enqueueing the **same key** does not dirty the row. New receipt/cause keys drive accumulation.

However, `salesOutreach/enrollment/admissions.ts:16–25,59–94,155–157` reads completed `outreach_lead_change` results with `created`, `not_admitted` and `deferred` outcomes as the only 14-day admissions/refusal history. A blanket deletion older than three days would make days 4–14 appear empty while the API still promises 14 days. The model's comment calling completed jobs operational exhaust is incomplete for this reader.

**Immediate cleanup contract:** select only `status: completed`, valid `completed_at < fixed_cutoff`, correct deployment/database, and a positive allowlist of proven recomputable stages/results. The first useful cohort is `outreach_evaluate`; add `outreach_lead_change` only for positively recognized subject-refresh outcomes `updated` and `unchanged`, after replay proof. Keep admission outcomes, unknown/legacy result shapes, and all nonterminal rows. A conservative first pass can preserve the entire lead-change stage if the inventory is ambiguous. Preview exact counts, bytes estimate and outcome distribution before applying. Never delete by `createdAt` alone.

**Sustained policy:** retain compact admission outcomes independently before reducing those job lifetimes, or preserve a longer retention class for them. Prefer a terminal `purge_at` stamped by a versioned persisted retention policy, with one zero-second TTL, rather than a universal three-day `completed_at` rule. Backfill it in bounded batches. During migration the existing 14-day TTL is an upper bound; do not promise longer retention until the old TTL has been changed in a reviewed index migration. Keep unknown classes unstamped. Policy lives in Mongo, per the mission constraint.

Other readers require explicit replay checks:

- `subjects/store.ts:409–418`: `creationJobSettled` treats a missing creation job as settled. Deleting a completed one is not equivalent to deleting pending or failed work.
- `salesIntelligence/nudges/repair.ts:51–60`: orphan repair generation comes from preceding repair jobs. This stage is receipt reconciliation only, never a resend, but should not enter the first cleanup allowlist.
- `numberActivity/callLogRefresh.ts:216+`: a persisted completed refresh dedupes provider work. Shorter retention permits a very late replay to nominate again; the worker's canonical-call guards must be proven after deletion.
- Evaluation sweep dedupe reads are job-key based (`evaluation/evaluateJob.ts:279+`). Deleting old jobs may recreate a still-due cause if projection state was not advanced. Monitor recreated keys and do not treat TTL alone as a work suppression mechanism.

Rollback cannot restore deleted job history from a code revert. The pre-apply backup/export and preserved admission facts are the rollback boundary. A sustained retention rollback only stops future expiry.

### OR-3 — RingCentral capture already has meaningful no-op guards; preserve them

`numberActivity/persistInteraction.ts:270+` returns before writes when the projection is unchanged, there are no merges and no missing aliases. Purged canonical interactions are retained as identity tombstones, so late provider replay does not resurrect content (`:235+`). `numberActivity/leadLinkJobs.ts:45–72` fingerprints only semantic Lead link inputs and deliberately excludes `updatedAt`.

`ringcentral/repSms/evidenceStore.ts:65–115` refuses stale provider modifications and returns `unchanged` on equal material evidence before CAS/update. `repSms/mailboxSync.ts:244` wakes only inserted/updated rows. SMS evidence is metadata only; body/subject/attachments are not stored, and status history is capped at 20 (`models/salesOutreach/repSmsEvidence.ts:15–40`). Do not propose body stripping or generic replay dedupe as if these protections were absent.

**Read-cost opportunity:** `numberActivity/callSummary.ts:131–196` loads every counted call for a Contact Number and folds it in application memory inside capture's transaction. A changed call can recompute a summary even when its summary contribution is unchanged. Add a contribution-change guard first: compare before/after summary-relevant fields, number membership, merge/tombstone state and settlement state. Recompute both old and new numbers when membership changes. Preserve the full recompute for late corrections, merges and retention. Only consider incremental summaries after benchmarks prove a need and replica parity covers late calls and revocation; the present recomputation deliberately ensures correctness.

**Legacy qualification diagnostic path:** `ringcentral/call-candidate-store.ts:30–122` upserts the per-party candidate on every event and appends a decision for each call to `storeRingCentralCallCandidateDecision`. No TTL is declared in its index builders (`:358–393`). Session decisions already append only on status transition (`call-session-store.ts:33–125`), but the session aggregate itself is updated each pass and its indexes have no TTL. Confirm whether this path is enabled and materially growing in production before prioritizing it. Proposed reduction is transition/error-only diagnostic decisions plus a bounded recovery horizon for candidates, not removal of qualification authority. Existing `ringcentral_processed_calls`, immutable Lead qualification and canonical interaction aliases must remain.

The live inventory gives this legacy path low priority: `ringcentral_call_sessions` is empty, and candidate/decision collections are not present in the collection list. By contrast, the bounded raw receipt store has 35,962 documents and approximately 68.98 MB allocated including indexes, with 30.67 MB free inside its data allocation. Rep SMS evidence has 12,451 metadata rows and approximately 4.26 MB including indexes. Preserve these functioning capture/credit stores while first addressing the much larger CSI job stream.

### OR-4 — future Call activity retention throughput is too small for a busy business

The current Call activity retention runs daily (`vercel.json:135`) and handles **50 interactions and 50 Numbers per run by default, with a hard maximum 100 each** (`salesIntelligence/retention.ts:41,55,65`). It redacts payloads and preserves identities. If more than 50 Calls/day age across the configured retention window, the backlog will grow once that window reaches mature data. This is a capacity defect in the long-term retention design, not evidence that it drives today's disk growth.

The default activity window is 730 days, with persisted policy override. Measure actual eligible count and daily arrivals before changing it. Replace the single tiny daily pass with a time-budgeted cursor/drain whose sustained service rate exceeds aging intake and whose transaction lease is renewed/fenced. Keep provider IDs and aliases. Record eligible backlog, oldest age, scanned/purged/failed counts and daily progress. Do not shorten Call/SMS history without a reporting/correction contract.

Hiding an index tests query dependence but does not save index bytes or write maintenance; dropping is the saving step.

Shorter card retention and removal of redundant historical no-op display cards could be safe after exact cohort analysis, but not from the collection name alone.

## Implementation plan and release proofs

1. **Measure and fix the cleanup manifest.** Inventory job stages/results/ages and existing TTLs. Split refresh jobs from admission history. Save a fixed-cutoff manifest and protected restore artifact. Rehearse bounded deletion against the local replica. Prove days 4–14 admissions/refusal results are unchanged. Quantify allocation reusable after deletion separately from filesystem space.
2. **Remove duplicate evaluator nomination.** Explicit sync result signal; preserve one durable evaluation for a changed or repaired subject. Replay tests cover unchanged, metadata-only, genuine policy transition, closed subject, Pool admission and interrupted worker. Confirm at most one evaluation cause for this transaction, no missed deadline repair, no changed policy periods or credit.
3. **Implement coalesced refresh state.** Requested/consumed generation with atomic claim/finish and recovery. Prove concurrent captures, claim expiry, crash after subject write, newer arrival during completion, stale/equal/newer Granot observations, same workflow 2→3, 0→5→0, uncertain priority resolved, Form/Call siblings, Pool eligibility and configuration changes. This work must not merge or skip Granot temporal acceptance.
4. **Terminal-job policy migration.** Persisted versioned retention settings, terminal classification, `purge_at` stamping and optional compact admission ledger. Backfill boundedly; compare old/new admissions reads before switching. Keep all nonterminal, unknown result and idempotency-authority rows. Replica replay after expiry must create no duplicate domain effects, provider sends, rep credit or duty credit.
5. **Optimize expensive no-op reads.** Summary contribution guard and bounded/cached-in-transaction performance-policy reads first. Benchmark p50/p95 transaction duration, examined/returned documents and work per receipt. Any optimization of historical SMS requirements must still apply explicit source corrections and preserve frozen coverage; do not just skip old dates.
6. **Long-term retention service rate.** Measure aging Call inventory, make draining bounded by time and cursor rather than 50/day, and observe backlog declining. Qualification diagnostic retention is a later change, justified by measured growth.

Release each slice separately with persisted feature/configuration control, qualified local replica evidence, deployment stamp and production observation. An application rollback must respect the Desk configuration schema's existing R0 rule for optional keys. Do not add unknown keys to `sales_outreach_configuration` and then roll back to a parser that rejects them.

## Acceptance metrics and unresolved evidence

- Complete November 14–15 CSI stage/status/result/cause counts quantify OR-1 above. They do not prove every unchanged evaluator can be removed; causal pairing and replay tests remain required.
- Three-day cleanup yield must exclude admissions results and all unclassified/nonterminal records. Earlier approximately 380 MB is a broad estimate, not the approved safe cohort's measured yield.
- Track new jobs per processed Granot receipt, evaluator outcomes, subject/projection modified counts, oldest pending/dead-letter age, and accepted-evidence-to-Desk freshness. Use bounded daily aggregates rather than adding per-receipt telemetry documents.
- Before and after release, compare exact persisted business outcomes: Lead qualification, Official Bookings/Cancellations, policy periods, deadlines, rep-day counts, SMS requirement outcomes, Pool winner credit and pending coverage. A reduction in rows alone is not correctness evidence.
- Verify live TTL indexes, expiry lag, legacy diagnostic writer activity, activity retention policy and pending jobs near raw-receipt expiry. Code declarations alone do not prove production behavior.
- Replica tests and deployment verification remain implementation gates. This report itself qualifies the code findings, not the proposed runtime changes.
