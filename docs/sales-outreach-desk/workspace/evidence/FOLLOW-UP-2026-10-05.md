### Defects the proofs found in production code (unit tests had masked both)

- **D1 — evaluation jobs with `input_revision: 0`.** `evaluationJob(subjectId, cause)` defaulted `inputRevision` to 0, and the `sales_intelligence_jobs` schema requires ≥ 1. Every caller that used the default would have thrown a Mongoose validation error inside its transaction: restriction add/confirm/lift (`commands/restrictions.ts`), the due-projection sweep and the policy-change sweep (`evaluation/evaluateJob.ts`), i.e. the minute `sales-outreach-evaluate` cron. Fix: the default is 1 and restriction nominations pass the restriction revision. Unit tests used in-memory stores, so the validator never ran.
- **D2 — parallel reads on one session inside a transaction.** `recountRepDay` (4 reads), `applyContactSources` (2), `plans.ts` `loadPeriods`/`loadPlans`, `subjects/sync.ts` (4) and `evaluateJob.ts` (6) issued `Promise.all` reads on the transaction's session. When they were the first operations of the transaction, Mongo refused the second `startTransaction` with `ConflictingOperationInProgress` (code 117: "Only servers in a sharded cluster can start a new transaction at the active transaction number"). A MongoDB session runs one operation at a time; all five sites now read sequentially.

### Proof fixes (test code only)

- P1 `reads.replica.ts`: the "no blocking sort" assertion inspected the whole explain output, whose *rejected* plans legitimately contain `SORT`; it now judges `queryPlanner.winningPlan` only (which is the `sod_projection_q_urgency` IXSCAN).
- P2 `contact-events.replica.ts`: the lease-held case acquired the competing lease on the wall clock while the sweep ran at a later synthetic instant, so the lease looked expired and was stolen; the proof now holds it on the sweep's clock.
- P3 — none beyond D2 (the proof itself was right about the concurrency case).
- P4 `reads.replica.ts`: a change stream opens its cursor lazily; the proof primed both streams (`tryNext()`) before publishing so the publishes land after the watch point. The SSE route is unaffected (it reads before reporting `connect`).
