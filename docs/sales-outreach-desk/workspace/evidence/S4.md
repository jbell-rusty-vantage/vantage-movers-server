## The six changes

1. **Rep-scoped cadence counts on `GET /rep-days`** (SPECIFICATION §6.1). Each row gains `overdue_leads`, `calls_due_today`, `sms_due_today`.
   - One per-Agent path for both reads: `teamCadence.ts` `composeRepCadence` → store `agentCadence(asOf, agentIds)`. `GET /team`'s `daily_call_goals[]` are the same composed rows, so they carry the same three values (the old `overdueFor` / `per_agent` path is gone; the team cards keep `teamOverdue`).
   - Overdue rule = the team card's: active subject, `queue_keys.urgency_due ≤ as_of` (shared `overdueFilter` in `deskStore.ts`), grouped by the projection's `assigned_agent_id`.
   - Due counts: sum of the stored channel `remaining` over the Agent's active Leads whose stored Call (or SMS) status is `due` or `overdue` (read-time derivation only turns `due` into `overdue`, so this equals the queue rows' "due or overdue"). Blocked, scheduled, pending, completed and not-required channels do not count. Review and closed subjects do not count.
   - Units: Leads (`overdue_leads`) vs call attempts vs SMS sends — stated in the schema comments.
   - Exposure, mirroring the team: cadence off → all three `cadence_disabled`; unresolvable → `policy_unavailable`; **shadow → `overdue_leads` null (`cadence_shadow`), due counts served**. Why: the team serves its shadow attention rows with requirements and `remaining` (overdue status reads `due`); a due count shows no overdue label. Enforcement → all three.
   - Like the team cards, the counts are current at `as_of` whatever `business_day` is shown.
   - A Rep reads only its own row (unchanged; a foreign `agent_id` is refused before any cadence read).
2. **`schedule_day` on queue rows** (`GET /queue` and the team's `leads_needing_attention` rows). Copied from the stored `detail.schedule_day` (`QUEUE_PROJECTION` now reads only that detail key). It is null when the row's workflow is not `new`, or when the evaluator stored none. Nothing is recomputed.
3. **`permitted_views`.** `activity` for every desk role while the desk is available. `settings` for a Manager whenever the configuration is active (it follows `day_override`, the only content). Owner unchanged; a Rep never gets `settings`. Both values were already in `SALES_OUTREACH_VIEWS`.
4. **`cadence_summary` on `GET /capabilities`.** Served to every role whenever the configuration is active (also with the desk off), null otherwise. It is a 1:1 copy of `cadence.policy_version`, `new_days_1_3_calls`, `new_call_slots` (`calls_per_day` = number of `deadline_minutes`) and `sms_sequence`. `quoted` is null: the configuration holds no Quoted daily-call value, and the Quoted due minutes are not exposed. No minutes, rules, approval refs, migration or Owner-only controls; no text.
5. **Names in `history.assignment_changes`.** `from_agent_name` / `to_agent_name` (string|null) next to the ids. Resolution: the reviewed `sales_rep` link name at `as_of` (the existing batched `findReviewedRepNames`, now including the change ids), else the Agent record's name (new batched `findAgentNames`, only for ids without a link name), else null. That is two queries per read, never one per row.
6. **Installer can clear `migration.paused`.** While this lane worked, another session shipped `--migration-paused=true|false` to `main` (`a60d2664`, merged `805457bf`, release tooling). I rebased onto it and kept its single field, `InstallArgs.migrationPaused` → `buildFinal01Configuration({migrationPaused})`. That avoids two implementations. The later `--intake-admission-at` flag (`08d43b6a`) is untouched and coexists. The brief's spelling `--migration=running|paused` is added as an **alias** that sets the same field. Anything else → `--migration must be running or paused`. Giving both spellings with different values → `disagree`. Behaviour (from the shipped flag):
   - only `migration.paused` changes, and without either flag it is carried over;
   - dry run unless `--apply`; the plan prints `migration_paused`;
   - apply writes through `patchSalesOutreachConfiguration` from the installed revision (idempotency key from the content hash), after `assertProductionWriterMatchesDeployment`.

## Decisions made in the lane

- **`coverage_incomplete` on the two due counts.** A due requirement can have `remaining: null` (engine: no capture coverage on that channel and nothing verified, e.g. SMS before `outreach_contact_sms` has a watermark). A partial sum would undercount. A 0 would break the "never 0" rule. So `calls_due_today` / `sms_due_today` use the cadence-metric shape with one added reason, `coverage_incomplete` (`SALES_OUTREACH_DUE_TODAY_UNKNOWN_REASONS`). `overdue_leads` keeps the exact team enum (an overdue status already requires complete coverage). This is new on new fields only; the team's existing cadence fields are unchanged.
- **`schedule_day` null outside `new`.** The engine stores a schedule day for every workflow ("received date = Day 1, any workflow"), and `GET /outreach/:id` `policy.schedule_day` still shows it unmasked. Per the lane brief, the queue row shows it for `new` only. If the admin wants calendar age for Quoted rows too, the stored value exists; it would be a one-line change.
- **History name fallback.** `assignment.assigned_agent_name` is unchanged (link name only). The Agent-record fallback applies to history names only, so a former rep who lost the link still has a name.
- **Counts follow the projection's `assigned_agent_id`**, like the team cards. The queue's per-page `receiver_agent` re-check is for row visibility; during a reassignment lag a count can trail by one evaluation, but no row or foreign data is exposed.
