### Decisions made unattended (phase 2)

1. **`/capabilities` always answers 200** for a signed desk role, reporting `configuration_state` (`uninitialized`/`unavailable`/`active`), `desk_available` and `unavailable_reason`; the Owner keeps `settings`, `numbers`, `accounts` and `configuration_edit` (CONTRACTS: the Owner recovery path stays available). Only `/rep-days` and `/team` fail closed.
2. **Desk off = 503 `CONFIGURATION_UNAVAILABLE`** with issue `{path: "controls.desk_enabled", code: "desk_disabled"}` (uninitialized: `configuration_uninitialized`). No new error code was added to the CONTRACTS list. This applies to the Owner too.
3. **`goal_metrics_enabled = false` answers 200** with `reps`/`goals`/`daily_call_goals` null and `goal_metrics_disabled`; freshness is still served and no rep-day rows are read.
4. **Freshness/coverage tolerance 10 minutes** (`CAPTURE_CURRENT_TOLERANCE_MS`): calls are `fresh` while the Call Log watermark is within 10 min of `as_of`, and today's count needs coverage through `as_of − 10 min`. Engineering threshold (RINGCENTRAL-CAPTURE §8 uses 10 min for SMS; the reconcile runs every 5 min), not business policy.
5. **A rep with no rep-day row** is a recorded 0 only when the day's calls coverage is complete; otherwise `actual_confirmed: null` (`pending`). A row's 0 with incomplete coverage is also null; a positive count is shown as a lower bound with partial coverage. Coverage is the worse of capture coverage and the row's own `coverage`.
6. **Goal source:** past days prefer the row's frozen `goal_snapshot` when it carries a `configuration_version` (SPECIFICATION §13.4 snapshot rule); today, and past days without one, resolve from the active configuration so a prospective override shows immediately.
7. **Future `business_day` → 400 `INVALID_INPUT`** (`future_business_day`). Past days have no lookback cap.
8. **Rep foreign `agent_id` → 403 `FORBIDDEN`** (issue `foreign_agent`), not 404: an Agent id is not a customer record, and the refusal must be visible, never broadened (CONTRACTS).
9. **Not-on-roster Agents with a row** are listed after the roster, labelled "Not on roster", goal null, and excluded from team goal/actual/reps-at-goal.
10. **Count-scope labels:** `all_outbound` → "Outbound calls" (FAST-TRACK); `eligible_new_quoted` → "Outbound calls (New/Quoted leads)" (engineering label; FAST-TRACK names only "Outbound calls" and "Other outbound"). Reps without a row use the day's scope, else `all_outbound`.
11. **Team actual with pending reps** = sum of known reps with `incomplete: true` and `pending_agent_ids`; all reps pending → null; mixed count scopes on one day → null (`mixed_count_scope`).
12. **Granot freshness** = newest `granot_observations.captured_at` across observation kinds and normalization results; `observed`/`unknown`, no staleness threshold (no policy names one).
13. **Responses are not schema-parsed at runtime** (a parse failure would surface as a misleading 400); tests parse every route body and every example.
14. **`permitted_commands` lists deployed commands only** (Owner `configuration_edit`); `role_capabilities` carries the full P09 set so the admin can show future controls disabled.
15. `/capabilities` and `/rep-days` admit all three desk roles directly (`SALES_OUTREACH_ROLES`), not through a new capability, so `MANAGER_CAPABILITIES` still equals the p09b fixture.
16. Rep names come from the reviewed `sales_rep` link's `agent_name_snapshot` effective at `as_of`; `reviewed_link: false` when there is none.

### Decisions made unattended (phase 3)

1. **Same workflow is a no-op.** An accepted code whose workflow equals the active period's (a repeated code, or 0 confirming an intake-default New) opens no period, so the New arrival schedule (12:00 deadline) is not converted into a partial-day reentry. The subject's `priority` still shows the current code. CONTRACTS: "Repeated accepted priority yields no new period".
2. **Transition time.** A new period starts at the accepted observation's `captured_at` (`time_basis: accepted_observation_captured_at`), else at the Lead's `last_changed_at` (`entity_change_applied_at`), and never before the active period started. The first period of a subject starts at its enrollment boundary (`activation_boundary`).
3. **Closures are final.** Official Booking, Cancellation, Bad Lead or a mapped closure code opens a `closed` period and sets status `closed`. Nothing reopens it, including a removed booking or a later nonterminal code (P05h "no automatic reopening"; "authorized reopening" has no command in v1). Closure keys are `closure:<reason>:<ref>`.
4. **A Duplicate flagged on an enrolled subject** moves it to `review` (`duplicate`), not `closed`. Duplicate is an exclusion, not an approved closure authority.
5. **Received quality.** `unreliable` = arrival after the reference instant or before 2010-01-01 (engineering bounds); `missing` = no timestamp. Both → review, never enrolled by backfill or intake.
6. **Intake gate.** Admits a Lead that is:
   - created **and** received at/after `intake_admission_at`, from a non-legacy origin (`legacy_import`/`legacy_unknown` never);
   - eligible, not closed by priority, with an approved intake source, and with an unambiguous Job Number.
   Its boundary is the received time; cohort `intake:<gate ISO>`. A Granot-created Lead without a priority is enrolled as a visible `review` subject with no period (P05e "Priority needs review"); a malformed stored code is likewise review. Late-created historical rows go to the enrollment lists (MANUAL-START step 7).
7. **Intake sources.** `wordpress_form` (Form) → website_form, `ringcentral` (Call) → ringcentral_call, `best_relocation_sheet` → best_relocation, `vantage_admin` → manual, `granot_lead_created` → granot_created. Legacy and missing origins have no approved default → review, never guessed. **Open question:** should historical `legacy_unknown`/`legacy_import` Leads with no accepted Granot priority ever be enrollable? Today they land in the review list.
8. **Ambiguous identity** = another non-duplicate Form/Call Lead carries the same normalized Job Number. Such Leads go to review in backfill and are not admitted at intake. This is engineering's reading of FAST-01 "ambiguous identity".
9. **Priority uncertainty (P05e).** Detected as a Granot observation for the Lead's Job Number with `priority.valid: false` and a present `raw`, captured after the last accepted one. An invalid observation writes no Lead change, so the flag is noticed on the next refresh of that subject (tail or reconcile), not instantly.
10. **Bookkeeping-only refresh.** A Lead revision with no desk-relevant change updates `lead_revision_seen` (so the reconcile settles) but does not nominate `outreach_evaluate`.
11. **Backfill window.** In scope when the received New York date ≥ today − `backfill_lookback_days` (the cutoff date is inclusive, so 91 dates), or `backfill_include_upcoming_moves` and the Form Lead move date ≥ today. Both fields must be installed, else 503. The candidate scan prefilters on the stored `timestamp` with a one-day slack, which is a superset because a wall clock is never later than the instant.
12. **Manifest.** sha-256 over algorithm version, kind, cohort id, configuration version and the canonical Lead ids.
    - The Idempotency-Key is the run key; a new run recomputes the manifest against the current configuration (mismatch → 409 `REVISION_CONFLICT`).
    - An existing run is resumed by its stored manifest only, so a later configuration change never blocks a resume.
    - Each Lead is re-validated at write time; a change after the report is skipped and recorded, never enrolled.
13. **`migration.paused` is honoured.** Apply is refused while paused (503 `CONFIGURATION_UNAVAILABLE`, issue `migration_paused`), and a pause between batches stops the run (`paused`). **The RELEASE agent must PATCH `migration.paused: false` before the FAST-01 backfill**; the FINAL-01 installer carries the current value over.
    - The telemetry-dependent migration limits (oplog/replication lag, all null) are **not** gated: FAST-01 overrides the slower launch mechanics and no telemetry reader exists. **Open question** for the Owner/RELEASE: measure them before cohorts of many thousands (IMPLEMENTATION-PLAN §8 note).
14. **Batch size and pacing.** Batch size = `migration.batch_size` (25), capped at 100; `migration.interval_seconds` (10) between batches. One HTTP apply call runs up to `deadline_seconds` (default 600 s) and returns `running`; the CLI loops.
15. **Audit kind.** The enrollment start audit uses the retained CSI kind `job` (`sales_outreach_enrollment_started`); no new audit kind was added to the shared enum. Batch completion is recorded on the run row (counts, checkpoint, skipped list capped at 2,000), not as audit rows.
16. **Verify.** Writes `verify:<run_key>` (upserted, re-runnable). It checks the manifest, boundary, one active period, and that the first period is `activation` at the boundary.
17. **Stages.** `outreach_revision_reconcile` and `outreach_intake` are a cron pass and an inline gate, not queued job stages: only `outreach_lead_change` and `outreach_evaluate` are registered.
    - `outreach_evaluate` rows are nominated with no consumer. They stay `pending` until phase 4 / the evaluator wiring adds the handler and a drain.
    - Stage-directed claims mean no other worker picks them up.
18. **Reconcile cursor.** Stored in a new `cursor.outreach_subject_id` field of `sales_intelligence_sync_state` (strict sub-schema; one added line in `models/salesIntelligence/capture.ts`). The lease is in the same scope row.
19. **Crons run without `desk_enabled`.** They need only an active configuration: muting the desk (`desk_enabled: false`) does not stop subject maintenance, so turning it back on shows current facts.
20. **Engine policy adapter not added.** The S2 engine's `cadence` encoding still differs from `salesOutreachConfigurationValueSchema`. The adapter belongs with the evaluator wiring (phase 4 / `outreach_evaluate`). Phase 3 periods carry the workflow, `start_kind` and times the engine needs.

### Decisions made unattended (phase 4a)

1. **Adapter mappings** (both encodings are engineering-owned):
   - uniform working hours, and `quoted_open_minute` = opening (else fail closed);
   - reentry thresholds = `late_arrival_rule`; P10a Quoted activation cutoff = `quoted_same_day_cutoff_minute`;
   - the optional third call only on Days 1–3 (band split);
   - `intake_default_rule` must be native New / Granot-created review.
   The FINAL-01 value maps to S2's policy exactly.
2. **Exposure.** The full result is stored with an `exposure` marker. Reads mask through `presentProjectionExposure`, so the Owner keeps shadow misses for the MANUAL-START reconciliation. With both controls off nothing is evaluated and nothing is claimed.
3. **Write test.**
   - `result_fingerprint` = engine fingerprint + resolved-policy fingerprint + assignee/received/job facts. Capture coverage advancing and unrelated configuration changes (e.g. a day override) never rewrite rows, so `configuration_version` is the version at the row's last write.
   - A cadence/exposure change is caught by the policy reconcile (`policy_fingerprint`).
4. **Evaluation job identities** per cause: `r<subject revision>` (phase 3), `plan:r<n>`, `assignment:l<lead revision>`, `restriction:<id>:r<n>`, `due:<ms>`, `policy:<fp16>`. The handler always evaluates current state.
5. **Sweep.** Clock repair and policy reconcile share the minute evaluate cron. There is no lease on the reconcile cursor: nominations are idempotent, so a racing pass only moves the cursor. A projection whose job dead-letters stays due and is re-found each minute (bounded at 500).
6. **Contact-event `outcome`** is not in the S3 model. It is derived as `inbound_answered` → answered, `inbound_missed` → unanswered, else unknown. **P06b advisory warnings cannot fire on outbound attempts until S3 stores `outcome`** (open question for S3).
7. **P07g originating answered inbound** is null until S3 marks the creating call's contact event (open question for S3).
8. **Assignment history** = `receiver_agent` intervals from `entity_changes`, cut to the Agent's reviewed `sales_rep` link periods. With no recorded change, the current assignee holds from the epoch.
9. **Restriction interval.** It is effective from `createdAt`. Release is the lift (`resolved_at`), `until`, or an `expired` row's last update; an active row with `until` releases at `until`. Channels: `text` → SMS.
10. **Plan revision** = the highest revision among the subject's plan rows. Each command adds 1 (the ended row and the new row share it), so Quoted and callback commands serialize; the unique active-plan index and the CAS on the active row fence races. No new index.
11. **Replacement intent** = `replace_active_plan: true`, else 400 `replacement_intent_required`. A Quoted reschedule of a Quoted plan and a callback `reschedule` need no flag. The same date or appointment is `changed: false`.
12. **Callback bounds.** An appointment more than 60 s in the past, more than 365 days ahead, or inside an active Call restriction → 400. SMS-only restrictions do not block a call appointment.
13. **Planning commands** need `desk_enabled`, a resolvable policy, subject `active` and an open (non-closed) period. Assignment refuses `closed` subjects and allows `review` ones.
14. **Rep scope at the command boundary** = the Lead's `receiver_agent` (authoritative), not the desk's copy.
15. **Assignment.**
    - `expected_revision` = `assignment_revision`. A desk copy that no longer matches the Lead's effective assignee → 409 `assignment_changed`.
    - The target must have a reviewed link. `null` unsets the receiver and stamps source `manual`.
    - A Manager is recorded in EntityChange provenance as DurableActor `admin` (there is no manager kind); the CSI audit keeps kind `manager`.
    - `lead_revision_seen` advances only if the desk was current. Lead-change + evaluate jobs are woken.
16. **Day override.**
    - "Prospective" includes today. A Manager's past date → 403 `FORBIDDEN` (`historical_edit_owner_only`); the Owner may edit any date.
    - The same agent/date is replaced.
    - Its own version id namespace (`…:day-override`) and audit kind `policy`.
17. **Restrictions.** All four routes are Owner-only (capability `lift_contact_restriction`).
    - Confirm keeps the row blocking and re-evaluates nothing.
    - Add needs an existing Contact Number and a future `until`.
    - New nullable fields on the retained model.
18. **`permitted_commands`** lists the deployed commands. Desk commands need the desk available; day override and restrictions need only an active configuration.
19. **`sod_subject_contact_numbers`** is a non-unique multikey index, so no write is fenced before the index is built. RELEASE builds it with `pnpm outreach:indexes`.
