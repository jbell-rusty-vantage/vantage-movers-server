## Verdict

## What I verified as correct

Confirmed against the code and the passing suites; not re-opened below.

- **`ownerRead(undefined)` default clock.** Every route calls `search(query)` / `detail(id)` / `timeline(id, opts)` with no `deps`, so `ownerRead(data, undefined)` falls through to `() => new Date()`. Works; `as_of` is populated on all three reads.
- **Search keyset vs `last_activity_at` range.** The range stays on the top-level `filter.last_activity_at` and the cursor predicate goes into a separate `$and` member, so both apply and the cursor cannot overwrite the range (`reads.test.ts` asserts it; the replica proof concatenates a nine-number same-instant cluster at limit 2 with no skips or duplicates). `last_activity_at` is `required: true` on the schema, so cursor encoding cannot hit an invalid date.
- **`keysetAfterCursor` for cross-kind same-millisecond pages.** The three branches are a faithful Mongo translation of `isAfterCursor` under `happened_at DESC, kind ASC, id DESC`: earlier kind → `$lt` time; later kind → `$lte` time (same instant is legitimately after); same kind → `$lt` time or same time with `$lt` id. Correct, and mirrored by a unit test.
- **Timeline dedupe and recorded-at.** `merged_into_id: null` is applied both in `interactionSource` and in `conversationSource`'s link scan, so a canonical interaction appears once and a tombstone never appears. `observed_at` is carried separately (`last_observed_at` for interactions, `createdAt` for messages and conversations). No body, transcript or summary text reaches any DTO, and `search_terms` is detail-only (strict schema + test).
- **Directory prune is account-scoped.** `Snapshot.find({ provider_account_id: accountId }).sort({ taken_at: -1, _id: -1 }).skip(bound)` cannot reach another account's snapshots. The raw-collection `deleteMany` is a deliberate, commented bypass of the append-only model hooks, and the count is reported in the summary.
- **Rebuild CAS and `resultFrom` placement.** `loadRebuildEvidence`, the `updateOne({ _id, revision })` CAS, the `$inc: { revision: 1 }` and the `number.rebuilt` audit all run on the completion transaction's session; `completeCsiJob` applies `resultFrom` to the mutation's return value *inside* that transaction, before the fencing `updateOne`. Concurrent capture and expired-lease fencing are both proven on the replica.
- **`$set: { rollups: next.rollups }` loses nothing.** `RebuildRollups` covers all eleven fields of `rollupsSchema`, so replacing the whole subdocument does not drop a stored field. `last_meaningful_contact_at` is copied through from the stored row rather than derived.
- **Rebuild is a genuine no-op on a healthy number.** The `provider_names` bound (push, then `shift()` above 10) matches `persistInteraction`'s rule exactly, and `sameRebuiltFields` compares `search_terms` order-insensitively, so a second rebuild bumps no revision and writes no audit.
- **`open_outreach` semantics.** `state !== "closed"` is right: `closed` is the only terminal member of `CSI_OUTREACH_STATES`. Detail and `loadRebuildEvidence` agree.
- **`conversationSource` fallback is index-backed and account-scoped.** The `{ provider, provider_account_id, provider_recording_id }` clause matches the unique `lead_conversation_account_recording_unique` index; a foreign account reusing a recording id is excluded.
- **Durable, not inline.** `POST /numbers/:id/rebuild` only enqueues through `executeCsiCommand`; the worker claims with `claimCsiJob(..., REBUILD_STAGE)`, so neither the drain nor `dispatchCsiWakeup` can steal Team C / CSI-11 stages.
- **Route guard and flag.** Mounted after `requireApiSecret` and after the boundary `use` middleware, and each handler re-checks flag + Owner + scope. Flag off is `404 FEATURE_DISABLED`; commands require `Idempotency-Key` (missing is 400); replay and `IDEMPOTENCY_CONFLICT` / `REVISION_CONFLICT` are proven through the real route stack.
- **No read mutates.** No `create` / `updateOne` / `save` / upsert in `search.ts`, `timeline.ts`, `contactNumbers.ts` or `coverage.ts`; coverage is two `find` calls plus one `countDocuments`. No read touches sync state or jobs. The replica proof's before/after byte snapshot over ten collections is a real assertion, and it passed here.
- **Boundaries held.** `numberActivity` reads Lead models only — no qualification, ingest or Lead-write imports. No recording / STT / LLM / Redis path, no Owner UI, no `outreach_ensure` / `attachment_refresh` / `recording_discovery` consumer, flags off in every runner.

## Findings

| # | Severity | Finding | How I confirmed it | Suggested fix |
| --- | --- | --- | --- | --- |
| 1 | **must-fix** | `search.ts` declares `hygiene: z.coerce.boolean().default(false)`. Under zod 4, `z.coerce.boolean()` is `Boolean(input)`, so every non-empty query string is `true`. `GET /numbers?hygiene=false` (or `0`, or `off`) returns `kind: { $ne: "external" }` — the Owner sees only company DIDs and extensions and **zero customer numbers**, the exact inverse of the documented contract ("Non-external kinds hidden unless `hygiene=true`"). A checkbox bound as `hygiene=${checked}` by Team E hits this on the default view. The existing unit test only passes `hygiene: "true"`, so the suite cannot catch it. | Ran `numberSearchQuerySchema.parse` + `buildNumberSearchFilter` over `{}`, `"true"`, `"false"`, `"0"`, `"off"`: only the absent key yields `kind: "external"`; all four strings yield `{ $ne: "external" }`. | Replace with an explicit string enum, e.g. `hygiene: z.enum(["true","false"]).default("false").transform((v) => v === "true")` (or `z.stringbool()`), and add `hygiene: "false"` / `"0"` to the `buildNumberSearchFilter` test. |
| 2 | **must-fix** | A directory that returns to a previously-snapshotted state is silently dropped and the stale snapshot stays authoritative. `runDirectorySyncOnce` compares the new digest only against the **latest** snapshot, but the model carries a unique index `csi_directory_digest_unique` on `(provider_account_id, digest)`. On A → B → A, the `create` fails with 11000, the handler treats it as "nothing new to record", reports `changed: false, error_code: null`, and sets `snapshot_id` to the *old* A row — while `loadDirectoryLookup` (latest by `taken_at`) keeps returning **B**. Capture then resolves party roles and company classification against a roster that is known to be wrong, with no error, no event and no coverage signal, until the directory reaches a state never snapshotted before or the A row falls off the 30-snapshot bound. Reverting states are ordinary RingCentral admin operations (extension disabled then re-enabled, DID unassigned then reassigned, queue member removed then added back). Note 02 §9 specifies "one document per successful directory sync", which would not have this hole. | Replica probe on `csi01`: three `runDirectorySyncOnce` runs with rosters A, B, A. Run 3 returned `{changed:false, digest:7aa87c9e, snapshot_id:<A>, error_code:null}`, only two snapshots exist, and `loadDirectoryLookup` still resolved `snapshot_id: <B>` (roster "Rep B") while the provider was serving "Rep A". | In the duplicate-key branch, advance the existing row so latest-by-`taken_at` is the current state (`Snapshot.collection.updateOne({ provider_account_id, digest }, { $set: { taken_at: takenAt } })`) and set `summary.changed = true`; or drop `digest` from the unique index and rely on the latest-digest comparison that the code already intends. Either way the branch must stop reporting a stale snapshot as the current one. |
| 3 | **must-fix** | `fanOutRebuildAll` is not retry-safe, contrary to its own comment ("re-running the same `all` job creates nothing new"). The per-number `dedupe_key` is stable (`csi:rebuild:number:<id>:all:<allJobId>`) but `input_revision` is re-read live on each attempt, and `enqueueCsiJob` folds `input_revision` into `payload_hash` and throws `IDEMPOTENCY_CONFLICT` on mismatch. So the first Contact Number whose revision moved between attempts aborts the whole batch transaction; the `all` job fails `transient` and can never succeed, retrying to `dead_letter` after 8 attempts. On a live account capture bumps revisions continuously, so any interrupted rebuild-all is unrecoverable. The failure is also mislabelled `worker_error`, hiding the cause. | Replica probe: seeded three numbers, enqueued the `numbers:all` job, ran it (`jobs_created: 3`), reset the job to `pending`, bumped one number's `revision` 1 → 2, re-ran. Attempt 2 returned `failed / transient / worker_error`, the job row went to `status: retry, attempts: 2`, and all three per-number jobs stayed at `input_revision: 1`. A direct probe confirmed the thrown code: same `dedupe_key` with `input_revision` 1 → 2 gives `IDEMPOTENCY_CONFLICT`. | Stop putting a volatile value in the fan-out payload: use a fixed `input_revision` (e.g. `1`, as `enqueueRebuildAll` already does for the parent job) and let the worker read the live revision, or catch `IDEMPOTENCY_CONFLICT` per number, count it as `existing`, and continue. Also map it to a distinct `error_code` instead of `worker_error`, and persist a resume cursor so a retry does not re-walk every number. |
| 4 | should-fix | Coverage capabilities are not honest against a failing stream. `readCaptureCoverage` projects only `scope`, `known_complete_through` and `gaps`, so `webhook: "ok"` means nothing more than "a `webhook_receipts` sync-state row exists" — which `MongoLeaseStore.acquire` creates on the recovery cron's very first lease, before any receipt is observed. `consecutive_failures` and `last_run.error_code` are ignored, and unlike `call_log` there is no timestamp to disclose staleness, so a dead webhook subscription is indistinguishable from a healthy one. `call_log: "ok"` has the same blind spot, mitigated only by `known_through`. The enum already offers `unavailable` and `denied`. | Replica probe: seeded `webhook_receipts` with `consecutive_failures: 7`, `last_run.error_code: "provider_request_failed"`, no cursor and no receipts, plus a `call_log_all_directions` row 3.5 months stale with `consecutive_failures: 9`. `readCaptureCoverage()` returned `{"call_log":"ok","recording_content":"unknown","webhook":"ok"}`. | Project `consecutive_failures` and `last_run.error_code` and degrade the capability (`"unavailable"` above a small failure threshold, or while `last_run.error_code !== null`). Consider surfacing a webhook watermark so `"ok"` carries an as-of the Owner can judge. |
| 5 | should-fix | `conversationSource` resolves conversations through a `CONVERSATION_LINK_SCAN_LIMIT = 2000` scan of the newest recording-bearing canonical interactions, and that scan **ignores the cursor**. On a number with more than 2000 such interactions, conversations linked to interaction 2001 and older are omitted from every page with no signal. The same 2000-row scan (projecting the full `recordings` array) is re-issued on every timeline page even when the page contains no conversations. | Code path: `timeline.ts` lines 327-334 — `.sort({ started_at: -1, _id: -1 }).limit(CONVERSATION_LINK_SCAN_LIMIT)` with no `keysetAfterCursor` term, while the conversation query itself is correctly keyset-bounded. Not reproduced end-to-end: it needs >2000 recording-bearing interactions on one number, which I did not seed. | Derive the scan window from the cursor (start the interaction scan at `started_at <= cursor.happened_at`), or key conversations directly off the number instead of through an interaction scan. If the bound is kept, report truncation in the page so the read stays honest. |
| 6 | should-fix | `leadMessageSource` matches `lead_messages` on `{ to: { $in: addresses } }`, and `LeadMessageSchema` declares no index on `to` — none of the eleven declared indexes covers it. Every timeline read therefore collection-scans `lead_messages`, then `$addFields happened_at` forces a blocking in-memory sort before the `$limit`. This is on the Owner read path for a production collection that grows with every outbound SMS. | Read all `LeadMessageSchema.index(...)` declarations (lines 188-219): `form_lead`, `observation_id+purpose`, `lead_ref.*`, `lead_source_company`, `granot_crm_source`, `twilio_message_sid(s)`, `status+next_attempt_at+createdAt`, `leased_until`, `purpose+status+createdAt`. No `to`. | Add `{ to: 1, sent_at: -1, createdAt: -1 }` (or `{ to: 1, createdAt: -1 }`) to the LeadMessage indexes and, if possible, sort on a stored field so the sort is index-covered rather than blocking. |
| 7 | should-fix | Rebuild **narrows** activity bounds where capture only widens them. `recountNumber` sets `first_observed_at = earliest canonical interaction` and `last_activity_at = latest canonical interaction`, falling back to the stored values only when there are no canonical interactions. `persistInteraction` is monotone in the other direction (`laterOf(...)` for `last_activity_at`, `next.started_at < row.first_observed_at` for `first_observed_at`). Whenever the stored window is wider than the canonical set — the extreme row is a merge tombstone, or was re-pointed to another Contact Number when a later Call Log revealed the real external number, or (per the handoff's own Team C note) Outreach activity advanced `last_activity_at` — a rebuild silently discards an observed fact. `last_activity_at` is the search sort key and the cursor key, so this also reorders the Owner's Numbers list. | Pure-function probe on `recountNumber`: stored `first_observed_at 2026-01-01` / `last_activity_at 2026-09-01` with interactions at `2026-03-01` and `2026-04-01` returned `2026-03-01` / `2026-04-01` — the window moved in two months and back five. I did not construct a production-realistic trigger, so the mechanism is confirmed but the exposure is not quantified. | Make the rebuild monotone like capture: `first_observed_at = min(stored, earliest)` and `last_activity_at = max(stored, latest)`. If deliberately narrowing is intended as repair, say so in the doc comment and record the prior bounds in the `number.rebuilt` audit (they are currently omitted from `prior`). |
| 8 | should-fix | Directory truncation is silent. `MAX_QUEUES_FOR_MEMBERS = 200` means queues past the 200th are stored with `member_extension_ids: []`, which reads as "this queue has no members" rather than "not fetched"; `queues.slice(0, 200)` uses raw provider order, so a reordered response also churns the digest and burns snapshot slots. `listAll`'s `hasNext = nextPage?.uri && records.length === PER_PAGE` stops paging when a page is short even though the provider advertised a next page, dropping the remainder with no error. Neither truncation appears in `DirectorySyncSummary` or on the snapshot. | Code read: `directorySync.ts` lines 260-286. Not triggered by the synthetic fetcher (one page, one queue), and not live-verifiable here. | Sort queues before slicing, add a `truncated` flag to the summary and the snapshot (or raise `ProviderFailure("page_limit")`), and drop the `records.length === PER_PAGE` conjunct so an advertised next page is always followed. |
| 9 | should-fix | The rebuild-all fan-out runs outside the job's completion transaction with no lease renewal across batches, so a long fan-out loses the lease and the `complete` call fails after the per-number jobs are already committed. Inside each batch transaction it issues 500 `findOne` + 500 `enqueueCsiJob` pairs, and `enqueueCsiJob` calls `assertIndexes` — an uncached `listIndexes` round trip — on every one of them, which is 500 extra commands per transaction and a real risk of exceeding `transactionLifetimeLimitSeconds`. | Code read: `rebuild.ts` lines 311-314 and 425-450; `jobs.ts` line 29; `transactions.ts` `assertIndexes` has no memoisation. | Renew the lease between batches, hoist `assertIndexes` out of the per-number loop (or memoise it per collection), and shrink `REBUILD_ALL_BATCH` or move the fan-out inside `completeCsiJob`'s session. |
| 10 | nit | The admin router's `fail()` returns HTTP 500 with `code: "INVALID_INPUT"` for any unmapped error (including `LEASE_LOST` and `INDEX_REQUIRED`), and `notFound()` returns 404 with `code: "INVALID_INPUT"`. Team E cannot distinguish a bad request from a server fault or a missing number. | Read `sales-intelligence-admin.routes.ts` lines 69-96. | Use a distinct code per shape (e.g. `INTERNAL_ERROR`, `NOT_FOUND`) and publish them in CONTRACTS. |
| 11 | nit | `fanOutRebuildAll` increments `created` / `existing` inside the `withTransaction` callback. `withTransaction` re-runs the callback on a transient write conflict, so the counters double-count and `jobs_created` / `jobs_existing` on the job result can exceed `numbers`. | Read `rebuild.ts` lines 435-447. | Accumulate per-batch counters inside the callback and fold them in only after the transaction commits. |
| 12 | nit | `readCaptureCoverage(_deps)` accepts a `CoverageDependencies` it never reads, and `ownerRead` dutifully threads a clock into it that is discarded. Dead parameter on a contract-published function. | Read `coverage.ts` lines 19-68. | Drop the parameter, or use it so `as_of` and the coverage read share one clock. |
| 13 | nit | `searchNumberActivity` calls `parseSearchTerm(query.q)` twice — once through `buildNumberSearchFilter`, once for `match`. | Read `search.ts` lines 135-143. | Parse once and pass the result into both. |

## Limitations

- **Live provider unverified.** Everything about RingCentral is synthetic or faked: directory list shapes beyond the fields read, real paging behaviour (relevant to finding 8), throttle semantics, production snapshot volume (the bound of 30 is only exercised as 3). No live directory grant is demonstrated by this patch or by this review.
- **Not exercised:** Vercel Queue delivery of rebuild wake-ups, production cron invocation, multi-node replica failover, and rebuild-all at production fleet size (findings 3 and 9 are the two places where scale matters most).
- **Findings 5 and 8 are code-path arguments, not end-to-end reproductions.** Finding 5 needs more than 2000 recording-bearing canonical interactions on one number; finding 8 needs a live provider response with more than 200 queues or a short intermediate page. Both are labelled should-fix accordingly.
- **Finding 7's mechanism is proven but its exposure is not.** The narrowing rule is demonstrated on the pure function; I did not build a production-realistic state that triggers it.
- **Downstream teams unverified by design:** Team C's Outreach / attachment mappers (detail returns empty `outreach_records`, `restrictions`, `review_items`), CSI-11 recording discovery, and Team E's client parsing of `NUMBER_DTO_FIXTURES`.
- CSI-03 was reviewed only for defects newly introduced by CSI-04's additive edits to the shared files. Its own behaviour was taken as already reviewed.
